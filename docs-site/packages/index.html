Packages · choose by boundary

Four packages, clear responsibilities.

The core package family is organized around four architectural boundaries. Optional integrations and tooling are packaged separately. Start with the runtime and providers for a normal application.

The package shape

The source tree is organized around Core → Runtime → Providers, with Extensions for optional framework integrations. 

Foundgine.Core
      ↓
Foundgine.Runtime
      ↓
Foundgine.Providers
      ↘
Foundgine.Extensions  (optional framework integrations)

Core packages and optional projects

Package Role Use it when
Foundgine.Core Provider-independent semantic model, metadata, intent, planning and execution contracts. You build semantic models, integrations or custom providers.
Foundgine.Runtime Application-facing orchestration, authorization, plan approval, routing and execution. You are building a normal Foundgine application.
Foundgine.Providers Concrete .NET storage (SQL, EF Core, in-memory, search), Redis shared state, Microsoft Agent Framework, events, gateway, AI/model, MCP and AOT provider integrations. You need physical infrastructure or agent/tool integrations.
Foundgine.Extensions Optional framework adapters: Hot Chocolate GraphQL, Keycloak identity and Temporal durable workflows. You need GraphQL, Keycloak or Temporal integration.

The .NET Foundgine.Providers package includes the Foundgine-owned ORM and Entity Framework Core provider assemblies, Redis and Microsoft Agent Framework adapters, and both source generators. Third-party dependencies are restored through NuGet declarations; third-party DLLs are not bundled in the Foundgine package.

Install the normal application stack

dotnet add package Foundgine.Runtime --version 3.4.0
dotnet add package Foundgine.Providers --version 3.4.0

Foundgine.Core is the provider-independent foundation and is brought in by the higher-level packages. Add it directly when your code intentionally targets its contracts.

Java / Maven

The Java artifacts use the io.github.cristianbarragan groupId and the repository has a Maven Central publishing configuration. The source POM version is 3.4.0; verify that the exact artifact/version is available in Central before pinning it, because the publishing configuration alone is not publication evidence. 

<dependency>
  <groupId>io.github.cristianbarragan</groupId>
  <artifactId>foundgine-runtime</artifactId>
  <version>3.4.0</version>
</dependency>
<dependency>
  <groupId>io.github.cristianbarragan</groupId>
  <artifactId>foundgine-providers</artifactId>
  <version>3.4.0</version>
</dependency>
<dependency>
  <groupId>io.github.cristianbarragan</groupId>
  <artifactId>foundgine-extensions</artifactId>
  <version>3.4.0</version>
</dependency>
<dependency>
  <groupId>io.github.cristianbarragan</groupId>
  <artifactId>foundgine-migrations</artifactId>
  <version>3.4.0</version>
</dependency>

foundgine-core is the provider-independent foundation and is brought in transitively by the higher-level artifacts. Add it directly when your code intentionally targets its contracts. foundgine-extensions is available the same way for optional framework integrations.

  • foundgine-core, foundgine-runtime, foundgine-providers and foundgine-extensions: main server implementation; source and tests are present, but the full Maven verification for this checkpoint remains pending.
  • foundgine-migrations: PostgreSQL schema diff and Flyway migration generation; source and tests are present, Maven/runtime verification is pending. See the module README.
  • foundgine-aot-generator: build-time annotation processor module, not a standalone runtime artifact.

The Central publishing configuration includes the Java artifacts above except the build-time-only foundgine-aot-generator.

Agent framework and Spring integrations

Optional adapters are included in the provider packages: Microsoft Agent Framework and Redis in .NET Foundgine.Providers; LangChain4j, Spring Boot and Redis in Java foundgine-providers. See Agent and framework integrations.

Client SDKs: TypeScript, Python and WebAssembly

Three thin transport clients talk to a running Foundgine server over MCP (Streamable HTTP, default path /mcp) and the Temporal workflow routes under /foundgine/workflows. They are not ports of the semantic runtime: identity, tenant, authorization, planning and providers stay on the .NET or Java server.

SDKPackageRuntimeSource
TypeScript @foundgine/typescript (npm) Node.js 20+ or any runtime with fetch src/typescript
Python foundgine-sdk (PyPI name) Python 3.11+, httpx; async and sync clients src/python
Rust / WebAssembly @foundgine/wasm (npm) Node.js 20+, browsers, Workers, Deno; host supplies fetch src/wasm

All three are development packages, not release-ready SDKs; the repository does not claim a registry release, so verify that a version exists on npm or PyPI before pinning it. See the client SDK overview for a comparison, a quick start and the verification status.

Optional integrations

Add Foundgine.Extensions for optional GraphQL, Keycloak and Temporal integrations. Choose the relevant capabilities inside Foundgine.Providers for SQL/PostgreSQL, InMemory, MCP or retrieval. The same package also includes Redis shared-state support and the Microsoft Agent Framework adapter.

Package boundary rule

Provider-specific concerns such as SQL syntax, PostgreSQL extensions, GraphQL parsing, MCP transport and model-provider integration should not leak into the provider-independent semantic contracts.
