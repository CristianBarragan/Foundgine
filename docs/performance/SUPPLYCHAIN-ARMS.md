# SupplyChain performance benchmark arms

This document is the implementation contract for `tools/foundgine-perf`.

## Four real implementations

| Runtime | Baseline | Foundgine |
|---|---|---|
| C# | Hot Chocolate + ordinary EF Core | Foundgine GraphQL adapter + Foundgine EF Core provider |
| Java | Spring GraphQL + ordinary JPA/Hibernate | Spring GraphQL + Foundgine JPA provider |

Each arm has its own PostgreSQL database. The four arms must execute the same runtime-specific GraphQL requests and authorization vectors. All four arms also use the same Redis 7.4 service with AOF (`appendfsync=always`); C# arms share the `benchmark:csharp:` key namespace and Java arms share `benchmark:java:`. Redis container CPU/memory usage is included in every arm sample. Do not substitute the CRM/ERP E2E application's domain model for the SupplyChain samples.

## Runtime-specific contracts

The C# request set is generated by `tools/foundgine-perf/scenarios/gen_supplychain.py` and targets the existing `src/csharp/samples/Foundgine.SupplyChain` domain. It covers:

- `salesOrder` reads with customer ownership filtering and role-dependent visibility;
- `catalogProduct` reads;
- `supplier` reads restricted to analysts/managers;
- `shipment` reads and operator/manager status updates;
- customer order creation, including denial when a customer attempts to order for another customer;
- mixed-identity requests in one benchmark cell, which must not leak authorization or row filters through a cached plan.

The Java request set targets the three-entity SupplyChain model in `src/java/samples/foundgine-supply-chain-advanced`: `Product`, `Supplier`, and `Warehouse`. It covers tenant isolation, analyst-only supplier risk fields, operator warehouse writes, and cross-tenant write denial.

These runtime-specific models are intentionally different. Parity means baseline and Foundgine are equivalent *within each runtime*, not that the C# and Java schemas are identical.

## Authentication and authorization

All four services validate Keycloak JWTs against the realm issuer and `supplychain-api` audience. The harness obtains tokens for named test identities. Each request must derive tenant and roles from validated claims; request-supplied actor or tenant values are not trusted. Missing tenant, missing role, invalid signatures, unsigned/edited tokens, and cross-tenant access must fail closed. Each arm performs Redis identity/digest revocation lookups bracketed by monotonic sequence checks against a PostgreSQL primary-backed durable high-water anchor. The Foundgine arms use the Redis revocation provider and anchored-store wrapper; the baselines use direct StackExchange.Redis/Npgsql (C#) or Lettuce/JDBC (Java) implementations, not Foundgine provider packages. Redis rollback, standby reads, anchor mismatch, and anchor/Redis outages fail closed. `/health/ready` includes Redis write/read/delete and PostgreSQL anchor checks.

C# authorization requirements are encoded in `tools/foundgine-perf/scenarios/vectors-supplychain-csharp.json`. Java requirements are encoded in `vectors-supplychain-java.json`.

## Migration provenance

- C# baseline: EF Core migrations generated from the baseline application's actual `DbContext`; applied with `Database.MigrateAsync`.
- C# Foundgine: EF Core migrations generated from the Foundgine EF provider's actual model; applied with the Foundgine sample's migration mechanism.
- Java baseline: Flyway SQL migration for the baseline JPA/Hibernate model.
- Java Foundgine: migration SQL generated by the repository's Foundgine JPA migration implementation and applied by Flyway.

No arm may call `EnsureCreated` or use Hibernate `ddl-auto=create/update`. The benchmark-only revocation epoch table is shared infrastructure: Foundgine arms create it with the provider migrator, while baseline arms create the identical table with their plain infrastructure initializer/Flyway migration. It is included in schema-parity output and must be identical within each runtime pair. Domain schema migrations remain owned by each arm's declared migration mechanism. Demo seed data is applied separately and deterministically.

## Readiness gate

A source scaffold or unit test is not a runnable arm. An arm is accepted only after all of the following are demonstrated:

1. application compiles with the repository's declared SDK/JDK;
2. its container starts against its own PostgreSQL database;
3. its own migration history table records the expected migration;
4. the schema dump matches its baseline/Foundgine pair;
5. Keycloak authorization vectors pass;
6. response-equivalence scenarios pass;
7. only then may performance measurements be reported.

## Redis and durable revocation parity

`compose/supplychain.yml` starts one Redis 7.4 service with AOF and a persistent named volume. `compose/supplychain.perf.yml` applies the same bounded CPU/memory allocation and publishes Redis for host-side diagnostics. `configs/supplychain-csharp.json` and `configs/supplychain-java.json` include the Redis container in each target's resource sample so the shared infrastructure cost is not omitted. The baseline projects intentionally implement the same Redis key layout and PostgreSQL `GREATEST` high-water update directly; the Hot Chocolate baseline explicitly references `StackExchange.Redis` and `Npgsql`.
